\title{Base: An Interface for Programming the Board}
\author{\url{https://github.com/unnamedlambda/base}}
\date{}

\begin{document}
\maketitle
\begin{abstract}
Base is an interface and system for programming at the scope of an entire board.
The CPU, GPU, network and file system are all controlled through a single
artifact loaded by a driver. Its compiled entry points can then be called at
run time, with the driver embedded through its C API and usable from Rust,
Python, C and Lean. Lean generators for artifacts have theorems which prove, at
build time, properties of the run-time behavior. Performance matches standalone
Rust on CPU workloads and PyTorch on GPU workloads.
\end{abstract}

\section{System Architecture}
\label{sec:interface}

Modern computer applications run on many devices at once, each with its own
control interface. A CPU has an instruction set, which a language like C is
compiled to directly. A GPU has a driver API, reached through system software
and usually programmed in a kernel language of its own such as CUDA~\cite{cuda}. Networks
and file systems are reached by system calls the CPU makes, with values computed
at run time. Each of these interfaces is precise in isolation, but real
applications require them to be composed together correctly. The programmer must
reason about CPU arithmetic, GPU kernel launches and their results, file paths
and the contents of writes, and above all about the interleaving of data between
these interfaces across the program's whole run.

For a single general-purpose device this is solved by an instruction set: a
finite, documented vocabulary through which the device's components are
controlled. A program for that instruction set is a standalone object,
independent of source details. Whether it was written by hand or generated by a
compiler, the same final object is the whole of the interface and governs the
resulting behavior. Base extends the scope of such an interface to the entire
board. A software driver accepts full board control via an \emph{artifact}: a
value that can be serialized, exist in memory, and be the subject of logical
reasoning.

\subsection{Artifact}
\label{sec:contents}

An artifact is represented as the Rust struct below and is encoded as the CBOR
data format~\cite{cbor}. It contains both a program and the memory it starts with.

\begin{codeblock}
\begin{lstlisting}[style=code,morekeywords={pub,struct,derive,serde}]
#[derive(Serialize, Deserialize, Debug, Clone, PartialEq)]
#[serde(deny_unknown_fields)]
pub struct Artifact {
    pub functions: Vec<clif::Function>,
    pub required_memory: u64,
    pub data: Vec<Segment>,
}
\end{lstlisting}
\end{codeblock}

A user decodes a serialized artifact, loads it, and calls an entry point by
name.

\begin{codeblock}
\begin{lstlisting}[style=code,morekeywords={let,mut}]
let artifact = Artifact::from_bytes(ARTIFACT_BYTES)?;
let mut driver = Driver::load(artifact)?;

let status = driver.execute("infer", input, output)?;
\end{lstlisting}
\end{codeblock}

The program is CLIF, the IR of the Cranelift code generator~\cite{cranelift}.
During load the driver JIT compiles the artifact's program to machine code and
initializes a shared arena according to the artifact's specification.
\texttt{required\_memory} is how much space to reserve for the arena, and the
segments of \texttt{data} are laid over it, so an artifact isn't forced to
specify every initial zero. Calls to \texttt{execute} invoke functions keyed by
the names the artifact carries, with the caller supplying both the input and
output pointers. The same arena is shared between calls, so state carries across
them: a device handle opened by one entry point is still open for the next.

\subsection{Driver}
\label{sec:running}

The CLIF program is a list of functions, each carrying an optional name for use
in \texttt{execute}. A function's blocks, block parameters and instructions are
encoded as data rather than as raw text. The driver walks that structure through
Cranelift's instruction builder to produce machine code. Only a subset of CLIF is
included: eight types, the widest a 128-bit vector, and
forty-five instruction forms spanning arithmetic, comparison, bit manipulation,
conversion, memory access, calls and structured control flow.

A CLIF program controls one core and the memory it addresses, and reaches for
\emph{primitives} to access the rest of the board. A primitive is a Rust
function using the C calling convention, compiled alongside the driver as part
of the Base crate. When an artifact is loaded, the driver hands Cranelift each
primitive's address to enable direct calls into these functions.

Device kernels can be embedded into the artifact as source text in its data
segments. The \texttt{cl\_gpu\_init} primitive leaves a device context at a
pointer into the arena; \texttt{cl\_gpu\_create\_pipeline} takes kernel source out of the arena
and gives it to the vendor's compiler; \texttt{cl\_gpu\_dispatch} launches the
result, and \texttt{cl\_gpu\_download\_ptr} writes what it computed back into
the arena. Figure~\ref{fig:lowering} follows both paths out of the artifact.
Kernel source and vendor driver use are handled entirely this way; Base has no
built-in device handling outside what a program reaches through these
primitives.

\subsection{C API}

The entire Base driver is exported as a C API, shown below. This
enables the driver to be embedded for calling from other languages, as C is the
common foreign function interface. Python and Lean APIs are built on top of
this.

\begin{codeblock}
\begin{lstlisting}[style=code,morekeywords={pub,unsafe,extern,fn,no_mangle}]
#[no_mangle]
pub unsafe extern "C" fn base_driver_load(
    artifact: *const u8, len: usize) -> *mut Driver { ... }

#[no_mangle]
pub unsafe extern "C" fn base_driver_execute(

\section{Programming Experience}
\label{sec:construction}

The driver's capabilities are accessed through the artifact, so it is clear why
the construction of an artifact must be done carefully. CLIF's instructions and
control-flow features have documented behavior, which enables reasoning about
correctness.

\subsection{Artifact Generation}

\emph{generator}. A generator relates to an artifact much as a C compiler

Lean~\cite{lean} serves as the interface from which artifacts are generated. Any
language or proof assistant which is capable of accessing Base through the C API
is a valid candidate for a generator, but no alternative has been implemented.
Artifact contents are Lean terms, serialized into CBOR and used with the driver
interface.

The program below replaces every NUL byte in a buffer with a space. Lean's
\texttt{do} notation over a \texttt{Prog} term binds values much as an IR
builder does in an application with an embedded compiler. The Lean here runs to
produce the artifact value, which is what performs the byte replacement.

\begin{codeblock}
\begin{lstlisting}[style=code,morekeywords={def,do,let,fun}]
def blend (v nul space : V .i8x16) : Prog V L (V .i8x16) := do
  bitselect (← icmp .eq v nul) space v

def scrub (vectors : Nat) (src dst : V .i64) : Prog V L Unit := do
  let nul ← splat .i8x16 (← iconst .i8 0)
  let space ← splat .i8x16 (← iconst .i8 32)
  forLoop (← iconst64 vectors) fun i => do
    let off ← ishlImm i 4
    let v ← loadI8x16 (← iadd src off)
    store (← blend v nul space) (← iadd dst off)

def code : Prog V L Unit := do
  scrub 256 (← dataPtr) (← outPtr)
\end{lstlisting}
\end{codeblock}

\subsection{Reasoning About Emitted Code}
\label{sec:constraints}

The intention of the scrub code above is to leave no NUL bytes in the buffer.
Below is a statement about the emitted instructions which are generated for the
artifact. Each input byte is confirmed to carry through to the output, with the
desired substitution performed.

\begin{codeblock}
\begin{lstlisting}[style=code,basicstyle=\ttfamily\footnotesize,upquote=true,
  morekeywords={theorem,def,by,fun,if,then,else,at,in},morecomment={[l]{--}}]
def Answers (Γ : Env) (c : Code) (binds : Nat) (v : V) : Prop :=
  ∀ (fuel : Nat) (cfg : Cfg) (w : World), ∃ Γ',
    runCode (fuel + 2) cfg Γ w c = .ok Γ' w
    ∧ Γ'.size = Γ.size + binds
    ∧ Γ'.back? = some v

theorem blend_leaves_no_nul
    (Γ : Env) (tys : List ClifTy) (hΓ : tys.length = Γ.size)
    (a b c : R) (xs : Array UInt64) (h16 : xs.size = 16)
    (ha : Γ[a]? = some (.vec .i8x16 xs))
    (hb : Γ[b]? = some (.vec .i8x16 (.replicate 16 0)))
    (hc : Γ[c]? = some (.vec .i8x16 (.replicate 16 32))) :
    ∃ ys, ys = xs.map (fun x => if x = 0 then 32 else x)
          ∧ Answers Γ (Prog.emit (discard (blend a b c)) tys) 2 (.vec .i8x16 ys)
          ∧ ∀ y ∈ ys, y ≠ 0 :=
  ⟨scrubLanes xs, rfl,
   fun fuel cfg w =>
     ⟨_, blend_scrubs fuel cfg w Γ tys hΓ a b c xs h16 ha hb hc, by simp,
      by simp [scrubbedBytes]⟩,
   scrubLanes_no_nul xs⟩
\end{lstlisting}
\end{codeblock}

The theorem above does not cover the splats or any behavior of the loop around
the blend.

\subsection{Accessing the Board}
\label{sec:coordinating}

A program that drives other device capabilities besides the CPU is written with
the same Lean interface. The following example renders a 4096$\times$4096
Mandelbrot set on the GPU and writes it to a bitmap file. The artifact's data
segments hold the GPU kernel source (the shader) and other values used at run time.

\begin{codeblock}
\begin{lstlisting}[style=code,morekeywords={def,do,let,fun,return}]
def code : Prog V L Unit := do
  let ptr ← basePtr
  gpuInit ptr
  let dataSz ← iconst64 pixelBytes
  let bufId  ← gpuCreateBuffer ptr dataSz
  let shOff  ← fldOffset f.shader
  let bdOff  ← fldOffset f.bindDesc
  let one32  ← iconst32 1
  let pipeId ← gpuCreatePipeline ptr shOff bdOff one32
  let wgx    ← iconst32 wgX
  let wgy    ← iconst32 wgY
  let _      ← gpuDispatch ptr pipeId wgx wgy one32
  let pxOff  ← fldOffset f.pixels
  let _      ← gpuDownload ptr bufId pxOff dataSz
  gpuCleanup ptr
  let total  ← iconst64 (54 + pixelBytes)
  let _      ← fldWriteFile0 ptr f.filename f.bmpHeader total
\end{lstlisting}
\end{codeblock}

\subsection{CPU Workloads}

Base with CLIF is level with Rust for the first three workloads. The other two
see Rust accessing capabilities that CLIF lacks support for: 256-bit vectors for
the polynomial and non-temporal stores for the copy. To close this gap, Base uses native
assembly, assembled in Lean and accessed using the \texttt{cl\_native\_load}
primitive.

\section{Limitations}
\label{sec:trust}

While Lean enables mechanical reasoning over the artifact and the code used to
generate it, the components of the infrastructure that it cannot cover are worth
considering. The model of CLIF is translated from the documentation and tested
against Cranelift on a corpus of 482 cases. The driver and the primitives are
implemented and tested in Rust, and no Lean proof can reach into these
implementations; it can only state assumptions about them, which can be reviewed
by hand.

Not every application can accommodate embedding the Base driver along with the
primitive implementations. Base is portable across x86-64 and ARM and uses no
features specific to one operating system, but platforms outside these are not a
fit, nor are applications that cannot accept the driver's cost at load: the most
expensive artifact in the repository takes 45\,ms to decode and 600\,ms to
compile.

\section{Conclusion}
Base enables programming at the scope of an entire system board. A single
interface accepts CPU control via CLIF programs, a shared memory arena, and a
selection of primitive functions CLIF can call, which cover device, network and
other board behavior.
The artifact and driver API allow Base to be embedded both in systems code, which
interacts with existing artifacts, and in proof assistants, which generate
artifacts and invoke the driver through its C API.
A Lean codebase allows programming applications at native speed while embedding
proofs about their behavior.
